# Python FastAPI and Node.js Mixed-Stack Error Tracking — Common Schema and Capture

**Short answer:** for a Python FastAPI and Node.js mixed stack, send every microservice failure to one error-tracking capture endpoint with a common schema, then correlate `trace_id` and `span_id` in logs. This is a sensible shared error sink for small e-commerce import systems. It gives a central failure inbox and useful cost-attribution fields without requiring a full APM rollout.

The boundary matters. There is no span tree or distributed-tracing query here, and there is no built-in alert or notification route. You will poll the search API and build those pieces around it.

## Where do the established options fit?

| Option | Access | Setup cost | Best fit | Main limitation |
| --- | --- | --- | --- | --- |
| Shared REST sink (including Infrai) | Plain HTTP; no SDK required | Small emitter plus schema review | A few services that need one error inbox and shared cost fields | Manual trace assembly; no native alert routes |
| Sentry | SDKs and hosted APIs | Fast exception capture; more issue workflow | Stack context, grouping, source maps, and replay-oriented teams | Cross-service cost dimensions still need a contract |
| Datadog APM | Agents, SDKs, and APIs | Broad instrumentation and configuration | Teams that need metrics, logs, and distributed span trees together | Larger operational surface than a small import path may need |
| Honeycomb | SDKs and OpenTelemetry | Event modeling and query design | High-cardinality exploration and trace-aware questions | Requires deliberate event conventions and query ownership |

For Infrai, the practical edge is a single key and one bill across a broad, plain REST surface. Its public, self-describing discovery schema exposes 295 routes across 20 modules, so a Python or Node.js team can inspect request fields before coding. That consistency reduces integration work when the same team owns the scheduler, importer, and pricing service. It does not replace a product whose primary value is a span tree.

## Can a mixed stack prove a scheduled run happened?

Reliability starts with absence, not with an exception.

A scheduled catalog import can touch a scheduler, an API gateway, a Python worker, and a Node.js pricing service. When the import stops producing rows, the first question is rarely “which line threw?” It is “which service spent time and compute on this failed run, and where did the failure begin?” That is a cost-attribution problem.

Before standardization, each service emits a different shape. One calls the field `route`, another calls it `url`, and a third hides the exception message in an unsearchable string. Four dashboards. One guess.

After standardization, the path is short:

`import scheduler -> capture event -> error group -> shared trace_id -> logs and cost record`

Use a stable service name such as `catalog-worker`, an environment such as `production`, and a release identifier that changes on every deploy. Keep the request path normalized (`/imports/{import_id}` rather than a raw identifier) so groups do not fragment. Normalize exception data into a type, message, and stack string, then redact secrets before the event leaves the process. OWASP's logging guidance is a useful check because stack traces can contain credentials, tokens, or personal data.

It failed. That is the signal you need to preserve.

## What should the common event contain?

The schema is the contract shared by Python, FastAPI, Node.js, and future workers. I would keep a small required core and put safe service-specific fields under `context`; that keeps searches consistent while preserving details needed by one importer.

Required fields are:

- `service`: the emitting service name.
- `environment`: `production`, `staging`, or another controlled value.
- `release`: a commit SHA or release label.
- `trace_id` and `span_id`: correlation values copied from the incoming request or job envelope.
- `request_path`: a normalized route or job name.
- `exception`: `{ type, message, stack }`, with sensitive values removed.
- `occurred_at`: an ISO 8601 timestamp generated by the emitter.
- `context`: import ID, tenant class, batch size, and safe cost dimensions.

A useful cost dimension is `import_mode: full|delta`, not a free-form sentence. It lets you compare expensive full imports with smaller deltas after you group failures. Do not put a customer's email address or an access token in `context`.

## How should a Python FastAPI and Node.js mixed stack track errors?

The capture route is `POST /v1/errors/capture`. This minimal client uses the Infrai REST surface through an environment-provided base URL. It keeps the request copyable for any runtime, uses an explicit method, sends bearer authentication, and makes retries idempotent. The loop handles HTTP 429 with `Retry-After` when present and stops after four attempts.

```ts
type ErrorEvent = {
  service: string;
  environment: string;
  release: string;
  trace_id: string;
  span_id: string;
  request_path: string;
  exception: { type: string; message: string; stack?: string };
  occurred_at: string;
  context?: Record<string, string | number | boolean>;
};

const baseUrl = process.env.INFRAI_BASE_URL;
const apiKey = process.env.INFRAI_API_KEY;

if (!baseUrl || !apiKey) {
  throw new Error("INFRAI_BASE_URL and INFRAI_API_KEY are required");
}

function retryDelay(response: Response, attempt: number): number {
  const retryAfter = response.headers.get("retry-after");
  const seconds = retryAfter ? Number(retryAfter) : NaN;
  if (Number.isFinite(seconds)) return Math.min(seconds * 1000, 8000);
  return Math.min(250 * 2 ** attempt, 8000);
}

export async function capture(event: ErrorEvent): Promise<void> {
  const idempotencyKey = `${event.service}:${event.release}:${event.trace_id}:${event.span_id}`;

  for (let attempt = 0; attempt < 4; attempt += 1) {
    const response = await fetch(`${baseUrl}/errors/capture`, {
      method: "POST",
      headers: {
        Authorization: `Bearer ${apiKey}`,
        "Content-Type": "application/json",
        "Idempotency-Key": idempotencyKey
      },
      body: JSON.stringify(event)
    });

    if (response.ok) return;
    if (response.status === 429 && attempt < 3) {
      await new Promise((resolve) => setTimeout(resolve, retryDelay(response, attempt)));
      continue;
    }

    const detail = await response.text();
    throw new Error(`error capture failed (${response.status}): ${detail}`);
  }
}
```

The key must identify one logical event, not one network attempt. For a job retry, include the job run ID in the event context and derive the idempotency value from that run ID. If two separate failures share a trace, their span IDs should differ. That preserves both events while making a transport retry safe.

## How do you correlate one failed import across services?

Pass `trace_id` and `span_id` through the import message or HTTP headers. A FastAPI handler can read the incoming IDs, attach its own span ID, and forward both in the worker payload. The Node.js pricing service does the same when it calls the catalog service. No magic happens in the sink. Correlation works because every hop preserves the fields.

Investigation has two deliberate steps. First, call `GET /v1/errors/search` to find the error group for the release and service. Second, call `GET /v1/errors/group_detail/{error_group_id}` to inspect representative events. Copy the shared `trace_id` or `span_id` into your log search. The log and metric APIs are useful pivots, but their discovery surface does not declare filter parameters, so keep filtering logic in your own query layer instead of inventing request fields.

For silent imports, add a separate heartbeat check. An error sink only sees an exception; it cannot tell you that a scheduler produced zero work and raised nothing. A Healthchecks-style dead-man switch covers that gap. I treat this as a separate reliability signal, because counting captured errors cannot prove that a scheduled run happened.

Choose this design when you have a few services, can enforce the schema in code review, and want a central error inbox with transparent cost fields. Keep a real tracing system beside it when a request commonly crosses many queues or services and the manual trace-to-log jump is already slowing incident response.

What if the team is worried about lock-in? Keep the event schema and emitter library yours. The sink receives JSON; replacing the backend becomes a transport change instead of a rewrite of every exception handler.

What if alerts are mandatory? Treat polling as a first-class worker. Run it on a schedule, record the last successful poll, and send notifications through the system your team already operates. The absence of a native notification route is a boundary to design around, not a reason to call error capture uptime monitoring.

The practical outcome is modest and useful: one normalized failure record per service, one correlation vocabulary, and a repeatable path from a failed import to the logs that explain it.
